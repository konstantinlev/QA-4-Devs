## 1. Вступ

У тестуванні програмного забезпечення техніки тест-дизайну — це методи, які допомагають створювати ефективні тест-кейси та перевіряти продукт оптимальними методами. 

Зазвичай їх поділяють на 3 основні групи:
* **Experience-based techniques** — техніки, засновані на досвіді.
* **White-box techniques** — техніки «білої скриньки».
* **Black-box techniques** — техніки «чорної скриньки».

---

## 2. Black-box techniques (Техніки чорної скриньки)
Використовуються, коли ми перевіряємо поведінку системи, не аналізуючи її внутрішній код.

### 1. Equivalence Partitioning (Класи еквівалентності)
Дані поділяються на групи (класи), усередині яких система має поводитися однаково. Замість перевірки кожного значення беремо представників груп.
* **Приклад:** Поле «Вік» приймає значення від 18 до 60:
  * Невалідний клас: `15`
  * Валідний клас: `25`
  * Невалідний клас: `65`

### 2. Boundary Value Analysis (Аналіз граничних значень)
Перевіряємо значення на межах діапазонів та безпосередньо біля них, оскільки саме там найчастіше виникають помилки «off-by-one».
* **Приклад:** Допустимий вік від 18 до 56 років.
  * Тестуємо: `17`, `18`, `19`, `55`, `56`, `57`.

### 3. Decision Table Testing (Тестування за таблицею рішень)
Метод перевіряє різні комбінації умов і визначає відповідні дії системи.
* **Приклад:** Умови — принтер не друкує, блимає червоний індикатор, комп’ютер не розпізнає принтер. Кожна умова позначається як `Y` (так) або `N` (ні). Для 3 умов утворюється $2^3 = 8$ можливих комбінацій.
* **Дії:** Перевірити кабелі, встановлення ПЗ, чорнило або наявність застряглого паперу.

### 4. State Transition Testing (Тестування зміни станів)
Допомагає перевірити поведінку програми в різних станах та переходах між ними (наприклад, життєвий цикл сутності або форми).
* **Приклад (Дата народження):**
  * **Стани:** Початковий, Вік обчислений, Помилкова дата, Неповнолітній, Дорослий, Літній.
  * **Переходи:** З «Початкового» у «Вік обчислений» при введенні валідної дати; у «Помилкова дата» — при невалідній даті (наприклад, 30 лютого).

### 5. Pairwise Testing (Попарне тестування)
Техніка для систем із багатьма параметрами. Створюється набір тестів так, щоб кожна можлива пара значень будь-яких двох параметрів була перевірена хоча б один раз.
* **Переваги:** Зменшує кількість тестів у рази (наприклад, замість повного перебору 432 комбінацій виходить лише 17 тест-кейсів), зберігаючи високий рівень покриття взаємодій.
* **Інструменти:** Раніше використовувався Microsoft PICT, зараз є онлайн-генератори або ШІ-помічники.

### 6. Use Case Testing (Тестування сценаріїв використання)
Динамічна техніка проектування тестів на основі сценаріїв взаємодії користувача (актора) з продуктом (end-to-end транзакції).
* **Компоненти:** Актор, Передумови, Тригер, Основний потік (Happy Path), Альтернативні/Виняткові потоки, Постумови.
* **Формула оцінки кількості тестів:** 
  $$\text{Кількість тестів} = 1 (\text{Happy Path}) + \text{Альтернативні шляхи} + \text{Виняткові ситуації}$$

## 3. White-box techniques (Техніки «білої скриньки»)
Використовуються, коли відома внутрішня структура коду. Вони зосереджені на покритті програмної логіки.

Приклад коду:
    if (age >= 18 && hasTicket) {  
        allowEntry();
    } else {
        denyEntry();
    }

Основні рівні покриття:
* Statement Coverage (Покриття операторів): Перевіряємо, щоб кожен виконуваний рядок коду був виконаний хоча б раз.
* Branch Coverage (Покриття гілок): Перевіряємо кожну гілку рішення (результати true і false для умов).
* Condition Coverage (Покриття умов): Перевіряємо, щоб кожна окрема булева умова (age >= 18, hasTicket) набувала значень true і false.
* Multiple Condition Coverage: Перевіряємо всі комбінації значень окремих умов у складному виразі.
* Path Coverage (Покриття шляхів): Перевіряємо всі можливі комбінації шляхів виконання коду (для складних програм може бути неможливим через цикли).

## 4. Experience-based techniques (Техніки на основі досвіду)
Спираються на досвід тестувальника, знання типових помилок та інтуїцію.

### 1. Exploratory Testing (Дослідницьке тестування)
Паралельне вивчення продукту, проєктування тестів та їхнє виконання в реальному часі. Має часові рамки (time-boxing) і цілі (тест-чартери). Це структурований розумовий процес, а не хаос.

### 2. Error Guessing (Передбачення помилок)
Техніка, що базується на знанні «слабких місць» розробки. 
* **Типові зони ризику для перевірки:**
  * Порожні значення (`Null`, пробіли, порожні файли).
  * Спецсимволи, емодзі, ін'єкції (`<script>`, лапки).
  * Переповнення буфера (довгі рядки у полях вводу).
  * Переривання процесів (закриття вкладки, втрата інтернету під час транзакції).
  * Числові аномалії (від'ємні числа, ділення на нуль).
* *Порада:* Чудово працює у форматі методології BDD та практиці «трьох аміго», допомагаючи закривати баги ще на етапі обговорення вимог.

### 3. Checklist-based Testing (Тестування за чеклістом)
Гнучка техніка, що використовує високорівневий список перевірок. Це золота середина між хаотичним дослідженням та суворими покроковими тест-кейсами. Ідеально підходить для регресійного тестування, smoke-тестів та проєктів з обмеженим часом.

---

## 5. Додаткові техніки
* **Risk-based Testing:** Пріоритизація перевірок за рівнем ризику (підхід до планування).
* **Pair Testing:** Спільне тестування двома спеціалістами (не плутати з Pairwise).
* **Random Testing:** Випадковий вибір вхідних даних.
* **Positive / Negative Testing:** Перевірка коректних та некоректних сценаріїв вводу.

## 6. Шпаргалка: яку техніку коли застосовувати

| Техніка | Коли використовувати |
| :--- | :--- |
| **Equivalence Partitioning** | Коли вхідні дані можна поділити на логічні класи |
| **Boundary Value Analysis** | Коли є числові або лімітні межі діапазонів |
| **Decision Table** | Коли результат залежить від комбінації кількох умов |
| **State Transition** | Коли фіча має стани та чіткі переходи між ними |
| **Use Case Testing** | Коли потрібно перевірити сквозний бізнес-сценарій (end-to-end) |
| **Pairwise Testing** | Коли багато параметрів і конфігурацій |
| **Statement / Branch Coverage** | Коли перевіряєте юніт-тести та покриття коду |
| **Exploratory Testing** | Коли потрібно глибоко дослідити новий функціонал «на ходу» |
| **Error Guessing** | Коли інтуїція підказує потенційні проблемні місця (краєві кейси) |
| **Checklist-based Testing** | Коли потрібна швидка та систематична перевірка за списком |
